This decision supersedes the earlier provisional Norway rankings and imported-colour meanings in documents 02, 03, 11 and 30. Meta and messaging automation remain deferred.

Call colours, in follow-up order: Orange Hot; Yellow Warm/itinerary sent; Purple Considering/details discussed without itinerary; Pink Busy/call back; Cyan No answer; Dark blue Repeated no answer. Red means Disqualified and leaves the calling lists. Green is derived from at least one positive non-reversed payment recorded on the enquiry, including unverified payments. Staff cannot choose green from the colour selector. This does not create a booking or verify funds. The explicit booking confirmation guard remains separate. Recording payment cancels pending tasks; source evidence and financial history remain intact.

The full row has a distinct background, strong coloured edge and a text outcome. New rows are uncoloured. Each row exposes contact, PAX/group/Schengen, priority, trip, colour, Note and optional follow-up. Save initial call / Save call atomically records the call, latest note, outcome and chosen follow-up. Previous pending tasks are completed (cancelled on disqualification), preserving their history. Save note only does not log a call. Save follow-up only creates/reschedules/cancels the follow-up without logging a call. Row details support group, Schengen and PAX qualification; the full profile retains contact/self-drive editing and financial actions. Row navigation excludes controls and text selection. Mobile uses stacked rows with the same controls. Daily summary and the existing sales pipeline remain under More views.

Writes use the typed command API, server-side scope checks, enquiry revisions and idempotency receipts. Optimistic updates cover call colour/list moves, notes and scheduling; failed saves restore saved state. Retryable ambiguous writes lock that row until the original request is retried or dismissed, preventing an accidental second call save. Payment preview also derives green immediately; verification and booking remain server-confirmed actions.

## Review reset

The user explicitly authorised removal of the existing enquiries and insertion of fictional review records. A private full D1 export was saved before the reset at `.wrangler/before-calling-reset-2026-10-30.sql`. It contains sensitive data and credentials hashes and must never be committed or shared publicly.

The reset is a one-off operational action, not a public reset endpoint. Existing enquiries are soft-deleted with reset attribution, their tasks/jobs cancelled, and all original customer/source/payment/booking history retained for recovery. Customer search retains existing contacts so staff can reuse a customer when entering a fresh enquiry. Active external source keys are archived into source JSON and released; linked import rows return to review with their previous association/review recorded in audit, allowing later reviewed re-import. Source files and import data remain private. Staff accounts, trips and workspace settings are retained. Norway receives the approved priority-rule version.

Sixteen clearly labelled Sample enquiries cover eight new records (including missing answers, all six ranks and Friends), six active follow-up colours, one disqualified record, and one converted record with an explicitly synthetic deposit. Contacts use reserved example numbers/email domains; messaging shortcuts are disabled on sample profiles and phone actions are disabled in sample rows. Sample deposits have no real receipt and do not create a confirmed booking. Managers can remove samples, including those with synthetic payments, through normal audited deletion. Real enquiries with financial records retain their deletion protection. The sample flag cannot be set through the public creation/edit schemas.

The reset SQL is first simulated against the recovery export with foreign-key and account/trip/finance-preservation checks. Its precondition checks enquiry revisions, payment/booking counts and the Norway trip version before writes. The private preparation script rejects a second run once review fixtures exist. Restore is operator-assisted from the export; there is no self-service undo screen.
